La app mobile implementa una **arquitectura offline-first**: los datos se leen primero desde la base de datos local (SQLDelight) y se sincronizan con el servidor cuando hay conectividad.

## Flujo de Datos

```
User Action → ViewModel → UseCase → Repository Implementation
                                        ├─ 1. Leer SQLDelight (local first)
                                        ├─ 2. Si miss/stale → Retrofit REST API (15s timeout)
                                        └─ 3. Guardar en local + emitir datos actualizados
```

<Steps>
1. **Acción del usuario** — El ViewModel invoca el UseCase correspondiente
2. **UseCase** delega al Repository
3. **Repository** lee primero datos locales (SQLDelight) y los emite inmediatamente
4. **Sincronización** — En paralelo, intenta obtener datos frescos del servidor (Retrofit, 15s timeout)
5. **Actualización local** — Si la red responde, guarda en SQLDelight y emite datos actualizados
6. **Sin conexión** — Si falla la red, los datos locales se mantienen sin cambio
</Steps>

## SQLDelight

La fuente exacta del esquema vive en `core/database/src/main/sqldelight/`. El cache actual incluye:

| Tabla | Uso |
| --- | --- |
| `Usuario` | Perfil local y hash para fallback offline controlado. |
| `EntidadPublica` | Catálogo local para formularios. |
| `Solicitud` | Bandeja SAIP, respuesta, timeline, consentimiento, canal formal de notificación, metadata documental y flags de sincronización. |
| `Apelacion` | Seguimiento TTAIP local para SAIP interna o apelación externa, con metadatos mínimos de elevación y documentos. |
| `Sesion` | Sesión local de trabajo; el JWT no se guarda aquí. |
| `SyncLog` | Reintentos de sincronización. |
| `Contadores` | Numeración offline transitoria. |
| `Notificacion` | Avisos locales y lectura. |

:::caution[Fuente de verdad]
SQLDelight mejora la experiencia offline, pero no reemplaza PostgreSQL ni decide reglas legales. La migración `migrations/2.sqm` hace opcional el vínculo con SAIP local y conserva metadatos mínimos de apelación externa y elevación.

La creación SAIP ciudadano conserva `consentimientoDatosPersonales` y `canalNotificacion` en caché. Las instalaciones existentes migran con `migrations/1.sqm`, verificada contra la instantánea inicial `databases/1.db`. Cuando una creación online responde correctamente, el repositorio reemplaza el registro provisional por el ID y número SAIP oficiales del backend; si no hay conectividad, mantiene el registro pendiente para sincronización diferida.
:::

## Bandejas Paginadas

Las bandejas activas no descargan miles de registros de golpe. Retrofit consume resúmenes livianos y SQLDelight conserva el respaldo offline:

| Rol | Solicitudes | Apelaciones |
| --- | --- | --- |
| Ciudadano | `/api/solicitudes/ciudadano/{id}/paginadas` | `/api/apelaciones/ciudadano/{id}/paginadas` |
| Funcionario | `/api/solicitudes/entidad/{id}/paginadas` | No aplica todavía |
| TTAIP | No aplica a su bandeja principal | `/api/apelaciones/paginadas` |

El sobre REST usa `contenido`, `pagina`, `tamano`, `totalElementos`, `totalPaginas` y `ultima`. La página `0` refresca el contenido visible; las páginas siguientes se agregan bajo demanda.

:::note[Cache sin pérdida de detalle]
Los resúmenes remotos se combinan con el registro SQLDelight existente antes de persistirse. Así se actualizan estado, expediente, fechas y canal sin perder consentimiento, descripción, timeline ni otros campos de detalle. Si falla conectividad se devuelve la página local equivalente; los errores HTTP reales se propagan para no ocultar rechazos del backend.

La bandeja TTAIP puede cachear una apelación externa creada en web sin depender de una SAIP local. Los actos de presentación ante entidad, elevación institucional y comunicación de omisión se envían online: SQLDelight conserva la consulta, pero no simula éxito administrativo offline.

El detalle agregado TTAIP se consulta desde backend y no se replica íntegramente en SQLDelight. Sala, miembros, resoluciones, cédulas, notificaciones, intentos, descargos, suspensiones, reprocesos, cumplimientos e historial requieren conectividad. De este modo la bandeja conserva un resumen útil offline sin convertir el dispositivo en fuente de verdad para actos legales ni evidencias institucionales.
:::

## Actuaciones Administrativas Online

Las operaciones SAIP de App Funcionario se envían directamente al backend:

- registrar observación;
- registrar ampliación con cronograma inicial;
- registrar encauzamiento total o parcial;
- emitir liquidación o cupón.

Estas operaciones requieren conexión. No se encolan como éxitos locales ni se ejecutan con actualización optimista porque generan actos administrativos sujetos a validaciones legales del backend. Si la conexión falla, la UI conserva el cache de consulta y solicita reintentar con conectividad.

La misma regla aplica a App TTAIP: calificación, subsanación, admisión excepcional, resoluciones, descargos, suspensiones, notificaciones, constancias, acuses, validación manual, reprocesos y seguimiento de cumplimiento solo se registran cuando el backend confirma la operación.

## Documentos

La integración documental usa exclusivamente el backend:

```text
OpenDocument -> ContentResolver -> multipart /api/documentos/upload
/api/documentos/{id}/download -> stream -> CreateDocument
```

- El archivo seleccionado se abre solo durante el upload y no se copia a SQLDelight.
- La descarga se escribe por stream en el destino elegido por el usuario.
- SQLDelight guarda únicamente metadata segura: ID, nombre, MIME, tamaño, hash, estado, fecha y tipo.
- Mobile no recibe ni persiste `storageKey`, bucket, endpoint, ruta física o URL S3.
- El provider local o S3-compatible es transparente para Android porque el backend intermedia las operaciones y valida ownership.

## Retrofit — REST API Client

```kotlin
// OkHttp con timeout de 15 segundos
val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(15, TimeUnit.SECONDS)
    .readTimeout(15, TimeUnit.SECONDS)
    .writeTimeout(15, TimeUnit.SECONDS)
    .addInterceptor(AuthInterceptor(credentialStorage))
    .build()

// Retrofit
val retrofit = Retrofit.Builder()
    .baseUrl("http://10.0.2.2:8080/") // localhost desde emulador
    .client(okHttpClient)
    .addConverterFactory(json.asConverterFactory("application/json".toMediaType()))
    .build()
```

:::note[IP del emulador]
En el emulador Android, `10.0.2.2` apunta a `localhost` de la máquina host. En dispositivos físicos, usar la IP de red local del servidor.
:::

## Mapper Pattern

Los Mappers convierten entre las 3 representaciones de datos:

```
Domain Model ←→ SQLDelight Entity ←→ Network DTO
     ↑              ↑                    ↑
  core/domain    core/database       core/network
```

```kotlin
object SolicitudMapper {
    // DB → Domain
    fun toDomain(entity: SolicitudEntity): Solicitud = Solicitud(
        id = entity.id,
        expediente = entity.expediente,
        asunto = entity.asunto,
        descripcion = entity.descripcion,
        estado = EstadoSolicitud.valueOf(entity.estado),
        fechaPresentacion = Instant.fromEpochMilliseconds(entity.fechaPresentacion)
            .toLocalDateTime(TimeZone.currentSystemDefault()),
    )

    // Domain → DB
    fun toEntity(domain: Solicitud, pendienteSubida: Boolean = true) =
        SolicitudEntity(
            id = domain.id,
            expediente = domain.expediente,
            asunto = domain.asunto,
            descripcion = domain.descripcion,
            estado = domain.estado.name,
            fechaPresentacion = domain.fechaPresentacion
                .toInstant(TimeZone.currentSystemDefault()).toEpochMilliseconds(),
            pendienteSubida = if (pendienteSubida) 1 else 0,
        )

    // DTO → Domain
    fun toDomain(dto: SolicitudDTO): Solicitud = Solicitud(
        id = dto.id.toString(),
        expediente = dto.expediente,
        asunto = dto.asunto,
        descripcion = dto.descripcion ?: "",
        estado = EstadoSolicitud.valueOf(dto.estado),
    )
}
```

## Sincronización Offline

<CardGrid>
  <Card title="pendienteSubida" icon="warning">
    Flag en la tabla local que marca registros creados offline que aún no se han sincronizado con el servidor.
  </Card>
  <Card title="Fire-and-Forget" icon="rocket">
    La sincronización se ejecuta en background (viewModelScope) sin bloquear la UI — si falla, se reintenta la próxima vez.
  </Card>
</CardGrid>

```kotlin
// Sync de datos pendientes
suspend fun sincronizarPendientes() {
    val pendientes = localDataSource.getPendientesSubida()
    pendientes.forEach { solicitud ->
        try {
            val response = remoteDataSource.crear(mapper.toDto(solicitud))
            // Actualizar local con ID del servidor
            localDataSource.insertOrReplace(
                mapper.toEntity(response, pendienteSubida = false)
            )
        } catch (e: Exception) {
            // Mantener como pendiente — se reintentará
        }
    }
}
```

## Seguridad Local

| Concepto | Implementación |
|----------|----------------|
| Credenciales | `EncryptedSharedPreferences` de AndroidX Security; sin fallback plano |
| Password hash | SHA-256 para login offline |
| Token JWT | Almacenado cifrado, no en SQLDelight |
| Logs | NUNCA loguear datos sensibles |
| Backup | Preferencias y base local excluidas de backup y transferencia |
| Timeout | 15 segundos en todas las llamadas de red |
