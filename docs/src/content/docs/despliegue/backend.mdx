PostgreSQL es el runtime principal en local, staging y producción. El schema
oficial es `database/postgres/script_saip_db_postgres.sql`; Hibernate usa
`ddl-auto=validate` y Spring no ejecuta seeds automáticamente.

## Variables de Entorno

| Variable | Descripción | Obligatoria |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | Usar `prod` en producción. | Sí en producción |
| `DB_URL` | JDBC PostgreSQL, por ejemplo `jdbc:postgresql://db:5432/saip_db`. | Sí en producción |
| `DB_USERNAME` | Usuario PostgreSQL. | Sí en producción |
| `DB_PASSWORD` | Password PostgreSQL. | Sí en producción |
| `JWT_SECRET` | Secreto HMAC de al menos 256 bits. | Sí en producción |
| `CORS_ALLOWED_ORIGIN_PATTERNS` | Orígenes web autorizados. | Sí en producción |
| `APP_NOTIFICATIONS_MODE` | `MOCK` local/Newman o `SMTP` producción. | `SMTP` por defecto en `prod` |
| `APP_NOTIFICATIONS_MAIL_FROM` | Remitente institucional. | Con SMTP |
| `SPRING_MAIL_HOST`, `SPRING_MAIL_PORT` | Servidor SMTP. | Con SMTP |
| `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD` | Credenciales SMTP. | Si SMTP exige auth |
| `APP_NOTIFICATIONS_PUSH_ENABLED` | Mantener `false` hasta Firebase Admin real. | No |
| `FCM_FIREBASE_SERVICE_ACCOUNT_PATH` | Ruta externa al service account. | Solo con FCM real |
| `FCM_TOKEN_ENCRYPTION_KEY_BASE64` | Clave AES externa para tokens push. | Solo con FCM real |
| `APP_STORAGE_PROVIDER` | `local` o `s3`. | No (default `local`) |
| `APP_STORAGE_LOCAL_BASE_PATH` | Directorio externo para binarios. | Sí con provider local en producción |
| `APP_STORAGE_S3_ENDPOINT` | Endpoint HTTP(S) S3-compatible. | Sí con provider `s3` |
| `APP_STORAGE_S3_REGION` | Región usada para firma S3. | No (default `us-east-1`) |
| `APP_STORAGE_S3_BUCKET` | Bucket documental aprovisionado externamente. | Sí con provider `s3` |
| `APP_STORAGE_S3_ACCESS_KEY` | Access key externa. | Sí con provider `s3` |
| `APP_STORAGE_S3_SECRET_KEY` | Secret key externa. | Sí con provider `s3` |
| `APP_STORAGE_S3_FORCE_PATH_STYLE` | Fuerza addressing path-style. | No (default `true`) |
| `APP_STORAGE_MAX_FILE_SIZE` | Máximo en bytes por archivo. | No (default 10 MiB) |
| `APP_STORAGE_MAX_REQUEST_SIZE` | Máximo del request multipart completo. | No (default 11 MiB) |
| `APP_STORAGE_ALLOWED_CONTENT_TYPES` | Allowlist MIME separada por comas. | No |

:::danger[Secretos]
No versionar passwords, JWT, `.env`, service accounts ni claves de cifrado.
Usar variables del entorno o un gestor de secretos.
:::

## Preparar PostgreSQL

PowerShell:

```powershell
$env:PGHOST = "localhost"
$env:PGPORT = "5432"
$env:PGDATABASE = "saip_db"
$env:PGUSER = "<local-user>"
$env:PGPASSWORD = "<local-password>"
.\scripts\postgres\run-postgres-schema.ps1 -RunTwice
```

Linux/macOS:

```bash
export PGHOST=localhost
export PGPORT=5432
export PGDATABASE=saip_db
export PGUSER='<local-user>'
export PGPASSWORD='<local-password>'
RUN_TWICE=true ./scripts/postgres/run-postgres-schema.sh
```

Los scripts rechazan nombres de producción y hosts remotos no confirmados. La
segunda ejecución valida idempotencia del DDL y del seed.

## Ejecución Local

```powershell
$env:DB_URL = "jdbc:postgresql://localhost:5432/saip_db"
$env:DB_USERNAME = $env:PGUSER
$env:DB_PASSWORD = $env:PGPASSWORD
$env:APP_NOTIFICATIONS_MODE = "MOCK"
cd backend
.\mvnw.cmd spring-boot:run
```

No se necesita un perfil PostgreSQL especial: la configuración base ya usa
PostgreSQL.

## Documentos

PostgreSQL guarda únicamente metadatos documentales. El provider local escribe
binarios fuera del repositorio y usa como default de desarrollo
`${user.home}/.saip-storage`. En producción, `APP_STORAGE_LOCAL_BASE_PATH` debe
apuntar a un volumen externo con permisos mínimos para el proceso backend.

Para un bucket S3-compatible, definir `APP_STORAGE_PROVIDER=s3` y las variables
de endpoint, región, bucket y credenciales. Si falta una variable obligatoria,
el backend falla al iniciar con un mensaje que identifica la variable, sin
imprimir su valor. `local` continúa siendo el default.

Tipos permitidos por defecto:

- `application/pdf`
- `image/png`
- `image/jpeg`
- `text/plain`

La API valida tamaño, extensión, tipo y firma básica, calcula SHA-256 y genera
una clave UUID antes de invocar cualquier provider. No expone rutas absolutas,
bucket, endpoint ni `storageKey`. El provider S3-compatible usa AWS SDK v2; no
crea buckets, no configura la consola de Supabase y no genera URLs públicas o
presigned. Las credenciales y archivos subidos nunca se versionan.

Ejemplo de activación, usando exclusivamente secretos externos:

```bash
APP_STORAGE_PROVIDER=s3 \
APP_STORAGE_S3_ENDPOINT=https://storage.example.invalid \
APP_STORAGE_S3_REGION=us-east-1 \
APP_STORAGE_S3_BUCKET=saip-documents \
APP_STORAGE_S3_ACCESS_KEY=secret_manager_reference \
APP_STORAGE_S3_SECRET_KEY=secret_manager_reference \
APP_STORAGE_S3_FORCE_PATH_STYLE=true \
java -jar target/saip-backend-0.0.1-SNAPSHOT.jar
```

### Validación real opt-in

La suite normal no se conecta a S3. Para validar un bucket real de staging,
definir externamente `RUN_S3_STORAGE_INTEGRATION_TESTS=true`,
`APP_STORAGE_PROVIDER=s3`, endpoint, region, bucket, access key, secret key y
`APP_STORAGE_S3_FORCE_PATH_STYLE`. Puede usarse
`APP_STORAGE_S3_TEST_PREFIX`; su default es `integration-tests`.

El endpoint debe copiarse de la configuración S3 de Supabase Storage o del
proveedor S3-compatible elegido. No hardcodearlo en el repositorio. El bucket
debe estar aprovisionado previamente: ni el backend, ni la prueba, ni los
scripts crean buckets o cambian permisos.

PowerShell:

```powershell
$env:RUN_S3_STORAGE_INTEGRATION_TESTS = "true"
# Cargar las variables APP_STORAGE_S3_* desde la sesión o gestor de secretos.
.\scripts\storage\validate-s3-storage.ps1
```

Linux/macOS:

```bash
export RUN_S3_STORAGE_INTEGRATION_TESTS=true
# Cargar las variables APP_STORAGE_S3_* desde la sesión o gestor de secretos.
bash ./scripts/storage/validate-s3-storage.sh
```

La prueba opt-in crea un texto controlado con key
`integration-tests/<uuid>.txt` o el prefijo externo indicado, comprueba
existencia, descarga, contenido y SHA-256, y elimina el objeto incluso si una
validación intermedia falla. No usa documentos reales ni persiste binarios en
PostgreSQL. Los runners no imprimen credenciales, bucket o endpoint y no
escriben archivos `.env`.

## Producción

<Steps>
1. Aprovisionar PostgreSQL y ejecutar el schema mediante un proceso controlado.
2. Cargar BD, JWT, CORS y SMTP desde variables o un gestor de secretos.
3. Aprovisionar un volumen local o un bucket S3-compatible y configurar solo el provider elegido.
4. Ejecutar tests y Newman contra staging.
5. Iniciar con `SPRING_PROFILES_ACTIVE=prod`.
6. Verificar salud, logs y ownership antes de exponer tráfico.
</Steps>

Ejemplo:

```bash
DB_URL=jdbc:postgresql://db.internal:5432/saip_db \
DB_USERNAME=saip_user \
DB_PASSWORD=secret_manager_reference \
JWT_SECRET=secret_manager_reference \
CORS_ALLOWED_ORIGIN_PATTERNS=https://misaip.gob.pe \
APP_NOTIFICATIONS_MODE=SMTP \
APP_NOTIFICATIONS_MAIL_FROM=no-reply@misaip.gob.pe \
SPRING_MAIL_HOST=smtp.example.net \
java -jar target/saip-backend-0.0.1-SNAPSHOT.jar \
  --spring.profiles.active=prod
```

## Newman

El runner prepara y verifica PostgreSQL, arranca el backend normal en modo
`MOCK`, ejecuta Newman y detiene el proceso:

```powershell
.\scripts\postgres\run-newman-postgres.ps1
```

Los reportes quedan en `postman/reports/`, que está ignorado por Git.

## Motor de Notificaciones

`MOCK` es exclusivo para local y Newman. Producción lo rechaza y usa `SMTP` por
defecto. `CASILLA_ELECTRONICA` sigue sin integración externa real y no existe
fallback automático. El adapter FCM no simula entrega y debe permanecer
deshabilitado hasta integrar Firebase Admin con credenciales externas.

## Checklist

- Ejecutar el schema oficial y validar `RunTwice`.
- Ejecutar `cd backend; .\mvnw.cmd test`.
- Arrancar sin perfil especial y validar `/v3/api-docs`.
- Ejecutar Newman con `APP_NOTIFICATIONS_MODE=MOCK`.
- En producción usar `ddl-auto=validate`, `spring.sql.init.mode=never` y secretos externos.
- Confirmar que la ruta documental está fuera del checkout y no es servida directamente por el web server.
- Con provider `s3`, verificar bucket, permisos mínimos y conectividad en staging sin publicar URLs directas.
- Mantener OpenAPI/Swagger deshabilitados en producción salvo aprobación operativa.
- No versionar dumps, reports, logs, builds ni credenciales.
